# 架构收敛工作流

只有预检发现架构重构、新状态权威、公共协议、重复实现或近义概念时才读取本文件。

## 一、确定问题

1. 列出重复类型、trait、字段、状态、协议和实现路径。
2. 分别证明定义、注册、运行时可达、消费者和已有验证。
3. 写清当前负面影响：行为分歧、双写、错误恢复不一致、公共接口误导或维护成本。
4. 没有具体负面影响时只记录改进建议，不把偏好升级成架构缺陷。

## 二、确定规范权威

1. 判断能力属于通用框架机制、使用方策略还是适配边界。
2. 选择一个最终规范类型、状态权威、协议或执行路径。
3. 公共框架接口不能因 EKO 未调用而删除；只有框架内部和合理复用方都不需要时才判定为死代码。
4. 适配器只能做无损转换、元数据注入和产品策略，不得拥有第二套调度、状态或重试语义。

## 三、比较方案

关键架构决策先调研业界成熟实现。至少比较：

- 扩展现有权威；
- 迁移到更合适的既有权威；
- 新建能力，仅当现有机制确实不能表达需求。

每个方案说明复用程度、公共接口影响、迁移风险、删除目标、验证方式和回滚边界。推荐方案必须解释为何
其它方案不能同时满足目标和边界。

## 四、设计迁移

1. 把迁移拆成有依赖顺序的阶段。
2. 每个阶段至少切换一条真实生产路径，不能只新增抽象。
3. 同阶段删除已被取代的旧实现、调用点、序列化字段、测试和文档。
4. 迁移期间只能保留轻薄适配器；剩余重复必须有明确下一阶段和删除条件。
5. 定义失败、取消、并发、恢复和部分副作用行为。

## 五、验收

- 新旧输入的功能与语义对等有字段级或场景级证据；
- 所有调用方已切换到规范权威；
- 旧实现和近义术语已删除；
- 公共接口、示例、文档和相关 Skill 已同步；
- 定向测试、完整门禁和必要的回滚验证已明确；
- 首个实际差异形成后继续调用 `semantic-diff`。

涉及新的公共契约、状态权威或多个可行取舍时，先调用 `brainstorm`，再按已确认方案调用 `design` 和 `plan`；
方案与计划闭合后才进入 `build`。不得用临时兼容层代替未完成的架构决策。
